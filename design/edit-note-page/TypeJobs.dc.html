B · Objects move to their type's folder by themselves

D-805 · amends D-226 · data-safety FR-STO-01 AC-7

No Move existing objects control, no offer, no confirmation. Saving a new folder in type settings moves the type's objects as part of the save. On vault open, and after each quiet period of the watcher, a tidy job moves every object that sits outside its type's folder (hand edits, sync, conversions made before 4E). Both make the backup first and report in the status element with Undo.

B1 · Type settings › General, the folder being changed
The tidy job waits for a quiet vault: it starts after the watcher has seen no change for a while, and re-checks each file at write time (FR-STO-01 AC-7). A file changed meanwhile, or with a pending conflict, is skipped and tried again at the next quiet period.

A taken name gets its (2) suffix and its links are rewritten silently (D-804). Two Macs tidying the same vault move to the same path; a differing suffix lands in the Conflicts view (FR-SYN-04). Every move is a sync upload, accepted.

C · A property's key never changes; only its Name does

D-806 · D-223 · FR-TYP-04 key rename is W

The Key in frontmatter of an existing property stays read-only for good. Name is the display name: it changes only the type file, no object is rewritten, and every file keeps its key. There is no key-rename job and no dialog.

C1 · Type settings › Properties › Status, the Name edited
Why: a key is the name in every file and in every other app that reads the vault (Obsidian properties, queries, scripts). Renaming it would rewrite every object of the type for a cosmetic change; the Name covers what the user sees. A new key means a new property, and Delete property with Remove values (section D) retires the old one.
The description Renaming keys comes in v1.0 becomes The key can't be changed after creation (types.md FR-TYP-03 AC-4; the test change is approved by D-806).

D · Deleting a property removes it everywhere

D-807 · supersedes D-228 · FR-TYP-04 · types.md AC-4

One dialog, no choice. Confirming removes the property from the type and its line from every object that has one, as one job: backup first, only those files written, undo in the status strip. There is no Keep values in notes: an orphan value is what a hand-written key is, not what a deleted property leaves behind.

E · A property's type can only widen

D-808 · supersedes D-227 retype and AP-18 · types.md FR-TYP-03 AC-11

No conversion, no preview, no misfit dialog. The Type menu offers only types in which every stored value stays valid as written (Number → Text, Select → Multi-select, …); narrower types are not in the menu at all. A widening retype writes only the type file, like any other schema edit. A narrower type is a new property.

G · Shared behaviour of every 4E job

Plan, then confirmThe dialog shows the counts the core planned: files, links, names that get a suffix. Cancel leaves the vault byte-identical.
Backup firstMulti-file jobs make the backup zip (D-57) before the first write; it is listed in Settings › Backups. A single-file type move does not.
Only the affected filesEach file is rewritten by a text edit of its own lines; bytes outside them stay. Files changed by another app meanwhile are skipped and listed.
Progress, not a modalThe status strip of 4C: count, Cancel while planning, then Undo for 5 s and in the palette. An open note gets its edits as one undo step in the editor.
Not updated listSkipped files show title, path and reason with Open, Retry and Retry all, as for links after a rename.
Never on system typesDaily Note, Tag, Image and PDF are neither targets nor sources of a type move; their built-in keys cannot be removed; no key is ever renamed (D-806).
